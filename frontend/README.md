# КДФП · Nuxt workspace для smeta-checker

Nuxt 4 / Vue 3 / TypeScript / Nuxt UI. Этот интерфейс работает с `backend/api.py` в этом же репозитории: `/api/v1`, постоянные проекты/версии/audit runs, Celery либо существующий fallback.

## Запуск

Единственный поддерживаемый запуск — Docker Compose из корня проекта
(см. [инструкцию для чайника](../docs/docker-quickstart.md)):

```powershell
Copy-Item .env.example .env   # заполнить POSTGRES_PASSWORD, AUDIT_API_TOKEN
docker compose up -d --build
```

Интерфейс: **http://127.0.0.1:3000**, API: **http://localhost:8000**.
Нативный запуск без Docker не поддерживается.

Development frontend: задайте серверные `NUXT_BACKEND_URL` и `NUXT_BACKEND_TOKEN`,
затем `pnpm --dir frontend dev`. Токен нельзя переносить в `runtimeConfig.public`,
браузерное хранилище или `NUXT_PUBLIC_*`.

## Пользовательский цикл

Главная (`/`): список постоянных проектов с поиском по проекту или ведомости,
сортировкой и вкладками «Активные» / «Архив». Строка открывает проект, а не
последний запуск. Название задаётся вручную; автоматического AI-именования нет.
Переименование не меняет UUID и ссылки.

В строке показаны количество ВОР, PDF и проверок, дата и ведомость последней
проверки, затем результат по позициям. Цветом выделены только результаты,
а не название проекта. Завершённая проверка без доступной сводки показывает
«Результат недоступен» с отдельным повтором загрузки, а не нулевые замечания.
Отсутствие проверок не означает, что документы не загружены.
На телефоне те же сведения располагаются последовательно под названием,
без горизонтальной прокрутки таблицы.

Переименование и архивирование находятся в меню «⋯» строки; архивирование
требует подтверждения. В архиве через это меню доступно восстановление.
Кнопка «Новый проект» находится рядом с заголовком списка проектов; в общей
шапке и пустом состоянии она не дублируется. Загрузка показывает скелетон
строк, ошибка списка и отсутствие результатов поиска имеют отдельные
состояния с повтором или сбросом поиска.

Архив открывается по `/?archived=true`; вкладки доступны и при пустом списке
или ошибке загрузки. Логотип и «Проекты» в шапке возвращают на `/` к активным
проектам. Кнопка «Назад» браузера восстанавливает просмотр архива.

1. «Новый проект» → название → «Создать проект». Внутри проекта — вкладки
   «Ведомости», «ПД» и «Проверки».
2. «Добавить документы» принимает несколько XLSX/CSV/PDF, папки с вложенностью
   через drag&drop или системный диалог. Пределы: 50 файлов, 100 МБ на файл.
   Перед сохранением для каждого файла явно выберите отдельный документ либо
   новую редакцию существующего. Совпадение имени не объединяет документы.
3. В карточке ведомости доступны реквизиты с источником (лист/ячейка), ручные
   уточнения, редакции и история проверок. Реквизиты извлекаются без OCR и
   LLM; неоднозначные поля остаются пустыми. Исходное извлечение и ручные
   уточнения хранятся раздельно.
4. «Проверить» выполняет preflight и запускает проверку по действующим
   редакциям всех проектных PDF — выбирать и подтверждать привязку не нужно.
   Обозначения из колонки «Ссылка на чертежи» сверяются с текстом ПД:
   отсутствующее обозначение даёт позиции статус «Ошибка» без вызова модели.
   При критических ошибках preflight требуется явное подтверждение, затем
   повторное нажатие. Каждая проверка — новый запуск со снимком конкретных
   редакций ВОР и ПД.
5. Новая ВОР сохраняет UUID ведомости даже при другом имени файла. Повтор тех
   же байтов в одном документе использует ту же редакцию. Новая ПД не
   подменяет действующую: выберите её явно кнопкой «Сделать действующей».
   Старые результаты, доказательства и Word продолжают открываться по прежним
   источникам.
6. Архив скрывает проект/документ без удаления; восстановление проекта не
   восстанавливает отдельно архивированные документы. Редакции, использованные
   в проверках, защищены от физического удаления.
7. Результаты содержат очереди, поиск/пагинацию, Word-отчёт и окно сверки.
   Excel-отчёта и ввода пути к папке нет; исходный XLSX можно скачать.
   В сверке PDF-навигация независима от вердикта; переход страницы не подтверждает
   позицию. На телефоне доступны отдельные вкладки ВОР и PDF.
8. Светлая и тёмная темы переключаются кнопкой в шапке. Общие семантические токены находятся в `app/assets/css/theme.css`; эталон экранов — pen.dev, см. корневой `AGENTS.md`.

Проверка оформления вызывается отдельно для выбранного листа XLSX, без LLM. CSV не выдаётся за редактируемую книгу Excel. ONLYOFFICE, сохранение редакторских ревизий и PDF-заметки в этой версии интеграции ещё не подключены.

## Контракты и проверки

```powershell
cd backend; python -m scripts.export_frontend_openapi; cd ..
pnpm --dir frontend run api:generate
pnpm --dir frontend run api:check
pnpm --dir frontend run fmt:check
pnpm --dir frontend run lint
pnpm --dir frontend run typecheck
pnpm --dir frontend run test:unit
pnpm --dir frontend run build
```

Источник схем — реальные Pydantic DTO в `backend/workspace_models.py`, `backend/audit_models.py` и `backend/api.py`. Сгенерированный SDK/TS/Zod находится в `app/generated/`; вручную его не редактируют. Экспорт OpenAPI не открывает БД и не запускает OCR/LLM.

Unit-тесты чистых функций и контрактов выполняются в Node, без запуска Nuxt. Пользовательские сценарии и компоненты проверяются E2E на собранном приложении.

Для E2E используется отдельная PostgreSQL `smeta_test_ui`, `backend/tests/workspace_server.py`, синтетические файлы и явно подменный тестовый LLM-клиент. Это испытание интеграции, не живой прогон модели. Начальный запуск требует пустую БД и новый `--root`; `--resume` использует уже созданный тестовый комплект без удаления данных. Обычный production entry point тестовый клиент не подключает.

После запуска fixture API на 8116 и built Nuxt на 3016 задайте `FRONTEND_URL=http://127.0.0.1:3016` и `E2E_FIXTURE_ROOT=<полный путь fixture>`, затем `pnpm --dir frontend run test:e2e`. GitHub Actions содержит эти шаги с отдельной тестовой БД.

## Как устроен запуск в Compose

Nuxt входит в общий `compose.yaml` как сервис `workspace`. Порт публикуется только
на host loopback (`127.0.0.1:3000`), внутри контейнера BFF доверяет Docker-шлюзу
(`NUXT_TRUST_PROXY=1`), сохраняя Host allowlist, same-origin и сессию.
`AUDIT_API_TOKEN` берётся из серверного `.env`.

BFF рассчитан на локальную работу и не является публичным многопользовательским входом.
